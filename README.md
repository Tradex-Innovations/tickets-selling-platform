# Encore event platform prototype

Encore is a production-quality frontend prototype for a connected, multi-vendor event marketplace and operations platform. It demonstrates event discovery, movie showtimes, reusable venue layouts, interactive reserved seating, checkout, QR ticket issuance, box-office selling, mobile check-in, seller operations, venue scheduling, and platform moderation against one shared local demo state.

The prototype is designed for presentations to organizers, cinema operators, theatre managers, venue owners, box-office teams, and commercial partners. All payments, delivery channels, identity checks, maps, exports, uploads, and camera scans are simulated; no live provider receives data.

## Technology

- Next.js 16 with App Router and strict TypeScript
- React 19 and Tailwind CSS 4
- Zustand with local-storage persistence
- React Hook Form and Zod validation
- Recharts reporting visualizations
- Lucide interface icons
- Accessible reusable UI primitives
- SVG seat selection and seating-plan builder
- Vitest and Testing Library setup
- Playwright browser workflow and responsive-layout tests

## Design direction

The customer marketplace is mobile-first, inspired by [GetTicket — Mobile Event Booking by Serkan Pehlivan](https://www.behance.net/gallery/228735441/GetTicket-Mobile-Event-Booking-App-UIUX-Design): deep-purple surfaces, vivid violet actions, poster-led discovery, swipeable event rails, and thumb-friendly bottom navigation. It retains the Encore identity and adapts into a full desktop layout, rather than reproducing a phone mockup. Mobile filters use a keyboard-accessible sheet; booking pages replace the bottom tabs with a dedicated booking action.

Seller, venue, box-office, check-in, and administration workspaces retain their separate light, data-oriented visual system with desktop sidebars. Check-in remains usable on phones. Marketplace theme rules are scoped to `.marketplace` so they do not recolor management tools.

## Installation

Requirements: Node.js 20+ and npm.

```bash
npm install
npm run dev -- --webpack
```

Open [http://localhost:3000](http://localhost:3000).

The repository uses Next.js's documented Webpack build option because some restricted environments prevent Turbopack's internal CSS worker from binding a temporary local port.

## Commands

```bash
npm run dev -- --webpack  # local development
npm run lint             # ESLint with zero warnings allowed
npm run typecheck        # strict TypeScript validation
npm test                 # domain behavior suite
npm run test:watch       # interactive test mode
npm run test:e2e         # Chrome browser workflow/responsive tests
npm run build            # optimized Next.js production build
npm start                # serve the production build
```

The browser suite uses installed Google Chrome by default and starts a development server automatically if needed. For CI or machines without Chrome, run `npx playwright install chromium`, then `PLAYWRIGHT_CHANNEL=chromium npm run test:e2e`. Tests use fresh browser contexts and do not reset your personal demo session.

## GitHub Pages deployment

The [GitHub Actions workflow](.github/workflows/deploy-pages.yml) checks the code, builds a static export, and publishes `out/` on pushes to `main`. This project is hosted from [Tradex-Innovations/tickets-selling-platform](https://github.com/Tradex-Innovations/tickets-selling-platform); its Pages address is [tradex-innovations.github.io/tickets-selling-platform](https://tradex-innovations.github.io/tickets-selling-platform/). In the repository, set **Settings → Pages → Build and deployment → Source: GitHub Actions** if it is not already selected. The workflow derives the URL prefix from the repository name and adds `.nojekyll` so GitHub serves Next.js's `_next` assets. Later pushes to `main` update the site.

The Pages build is an organizer-facing preview: it exposes only **Event organizer** and **Customer** in the role switcher. Admin, venue-manager, box-office, and check-in routes are not exported. The organizer can select an existing hall layout and request a new one from the platform team; the layout-request action is simulated. The full six-role demonstration remains available in local development.

For a local Pages export on macOS/Linux, run `GITHUB_PAGES=true NEXT_PUBLIC_ORGANIZER_PREVIEW=true NEXT_PUBLIC_BASE_PATH=/tickets-selling-platform npm run build`. On PowerShell, set `$env:GITHUB_PAGES="true"`, `$env:NEXT_PUBLIC_ORGANIZER_PREVIEW="true"`, and `$env:NEXT_PUBLIC_BASE_PATH="/tickets-selling-platform"` before `npm run build`. The export is in `out/`.

The hosted site is an **interactive prototype**: payment and identity steps are simulated. Browser storage is private to each visitor, so seller changes, seats, and tickets carry across roles only in that visitor's browser. Seeded and fixed demo-created event routes are exported for direct links and refreshes; arbitrarily new runtime URLs cannot be generated by static hosting. Use a server-backed deployment for real shared inventory, accounts, payments, or live ticket sales.

## Hosted organizer presentation

Open `/demo` and choose **Event organizer** to review the dashboard, concert, sales, hall-layout selection, ticket pricing, reports, and expected payout. Choose **Customer** to browse the published concert or movie, select seats, apply `ENCORE10`, pay with the simulated checkout, and open QR tickets. A newly submitted organizer event stays pending for off-stage platform review and will not appear in the customer marketplace until approved in the full local demo.

## Full local demonstration scenario

1. Open `/demo` and reset demo data if necessary.
2. Switch to **Event organizer**.
3. Open `/seller/events/create`, review the venue and layout steps, configure ticket pricing, then submit **Colombo Afterglow Live**.
4. Switch to **Platform administrator**, open `/admin/events`, and approve Colombo Afterglow.
5. Switch to **Customer** and find the newly published event in Explore.
6. Choose its session, open the seat map, and use **Find best seats** for an adjacent pair.
7. Continue to checkout and apply `ENCORE10`.
8. Complete the simulated card or wallet payment. A failed-payment toggle is available for the release/retry example.
9. Open the generated individual QR tickets in `/account/tickets`.
10. Switch to **Check-in staff**, scan the new valid ticket, then scan it again to show the already-scanned warning.
11. Switch back to **Event organizer** to view the updated sale, check-in, and expected settlement figures.

For the shorter cinema demo, use `/movies/serendib-skies` or `/seller/movies`. The 2:30 PM, 6:15 PM, and next-day showtimes have separate seat-state collections.

## Mock services and persistence

Centralized data lives in `src/data/mock-data.ts`. Shared domain models live in `src/types/domain.ts`, pure business rules in `src/lib/domain.ts`, and simulated integration boundaries in `src/services/mock-services.ts`.

Zustand persists meaningful state under `encore-demo-v1`, including roles, created/approved events, seat inventory, reservations, orders, tickets, check-ins, favorites, event-wizard drafts, and commission settings. Customer web bookings and box-office sales update the same session inventories. **Reset Demo Data** on `/demo` restores the seeded scenario.

All monetary values are integer minor units. LKR is the centralized default, while the formatter and admin setting leave a clear path to multi-currency support.

## Prototype limitations

- Authentication and authorization are interface simulations, not server security boundaries.
- State is browser-local and single-device; there is no concurrent server, database, or real seat-lock coordinator.
- Payment, email, SMS, wallets, QR cryptography, identity verification, document storage, maps, PDF/CSV exports, printing, and camera access are simulated.
- The layout builder demonstrates credible selection, multi-select, seat editing, blocking, duplication, movement, templates, zoom, undo/redo, preview, and version intent; it is not a CAD tool.
- Browser tests cover discovery, responsive layouts, role switching, customer payment, ticket issuance, and duplicate check-in. Seller moderation, transfer, failed-payment UI, and box-office contention still need dedicated browser scenarios; critical domain transitions are unit-tested.

## Backend integration recommendations

1. Move authentication and role claims to a managed identity provider with server-enforced organization and event permissions.
2. Store events, venues, versioned layout JSON, sessions, orders, tickets, check-ins, refunds, disputes, and settlements in a transactional relational database.
3. Implement seat holds with atomic database updates, expiry jobs, idempotency keys, and real-time session channels.
4. Put payment callbacks behind signed webhooks and create orders/tickets idempotently from verified provider events.
5. Sign ticket QR payloads or use short-lived opaque tokens; retain immutable scan and transfer audit records.
6. Add queued email/SMS delivery, wallet-pass signing, object storage, virus scanning, map/geocoding, finance exports, and observability.
7. Extend Playwright coverage to seller approval, box-office contention, transfer, refunds, and failed-payment recovery.

See `IMPLEMENTATION_STATUS.md` for detailed coverage and verification evidence.
